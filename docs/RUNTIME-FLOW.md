# Omni Nexus 실행 흐름 — Risu 위에서 무엇이 언제 도는가

기준 코드: `e1555e7`(되돌린 상태, `7dc6286`). 렉 작업은 이 문서의 순서대로 하나씩, 측정으로 확인하며 한다.

숫자는 실험실 측정이다. 가짜 Risu 화면(최신 메시지가 맨 앞인 Risu 배치, 메시지 40개, 8줄씩, 그림은 파일 주소)에
이 저장소의 실제 코드(TTS 줄 버튼·TTS 창·분홍 칸·플로팅 태그·플로팅 뷰어)를 올렸다. CPU는 폰처럼 4배 느리게 했다.
통로는 두 가지로 잰다. **하나씩**: 호출 하나가 왕복(3ms)을 마쳐야 다음이 출발한다(처음 잰 방식, 비관적).
**겹쳐**: 요청이 한꺼번에 날아가고 Risu는 온 순서대로 하나씩 처리한다(postMessage가 실제로 이렇다, 낙관적).
폰은 그 사이 어딘가다. 절대값은 다르니 **비교용**으로만 본다.

## 0. Risu 플러그인 v3에서 가능한 것과 그 값

| | 내용 |
|---|---|
| 구조 | 플러그인은 샌드박스 iframe. Risu 화면은 SafeDOM 프록시로만 만진다. **호출 하나 = postMessage 왕복 하나.** `release()`만 편도. |
| 읽기 | `x-*` 속성만 `getAttribute`. `data-*` 같은 건 `getOuterHTML`(통째)이나 `cloneNode(false)` 뒤 읽기로만. 위치는 `getBoundingClientRect`·`clientHeight`. `querySelector(All)`(`:has()` 포함). `cloneNode`. `MutationObserver`. |
| 이벤트 | 리스너는 **어디에 달든 문서 전체**에 붙고, 이벤트엔 좌표만 오고 대상(target)이 없다. 리스너 하나마다 이벤트를 따로 보낸다. |
| 없는 것 | `getProperty`, `elementFromPoint`, `closest`, `scrollTop` 읽기. |
| 폰 | Risu 화면과 플러그인이 같은 메인 스레드일 가능성이 높다. 그러면 플러그인 쪽 계산도 Risu 스크롤을 막는다. |
| 목록 풀기 | Risu의 `unwarpSafeArray`(`apiV3/factory.ts`)는 길이를 묻고 **항목을 하나씩 차례로** 묻는다: 항목 n개 = n+1번 기다림. 우리 것은 `src/core/util/safe-list.ts`(벤더 쪽은 `nxUnwrapSafeNodes`)로 한꺼번에 묻는다: 2번. |
| 없는 메서드 | 게스트 프록시는 **어떤 이름이든 함수**를 돌려준다. `el.getProperty?.()`도 실제로 호출돼서, Risu가 "없는 메서드" 오류로 답하는 왕복 하나가 된다. |
| 호스트 로그 | Risu 호스트는 호출마다 요청과 응답을 `console.log`로 남긴다(배포 빌드도). 호출 수와 주고받는 크기가 그대로 Risu 쪽 일이다. |
| 채팅 HTML | Risu의 DOMPurify가 `x-*` 속성을 지우고(`data-*`는 남김) 클래스 이름 앞에 `x-risu-`를 붙인다. 그림은 `[data-inlay-inline-shot]`로 찾아야 하고, `.inray-shot`으로는 안 잡힌다. `x-*`는 우리가 `setAttribute`로 쓴 것만 있다(이미지 기록의 `x-inlay-inline-shot` 등). |
| 채팅 구조 | `.default-chat-screen`(스크롤되는 상자, column-reverse) 안에 입력창 등과 메시지 목록 `div.flex-col-reverse`, 그 안에 메시지마다 `div[x-hashed].chat-message-container > .risu-chat[data-chat-index]`. 메시지가 바뀌면 Risu는 감싼 div를 새것으로 바꾼다. 첫 메시지(인사말)는 목록 밖 형제로 그려질 때가 있다. |

여기서 나오는 원칙:
1. **입력 경로(누르기·끌기·탭·스크롤)에서는 Risu에 묻지 않는다.** 위치는 미리 재서 들고 있다가, 바뀌었을 때만 다시 잰다.
2. **비싼 건 왕복 횟수**다. 데이터를 줄이려고 호출 수를 늘리면 오히려 느려진다(어제 내 수정이 이 실수).
3. 큰 읽기(캐릭터 전체, 모든 봇 DB, 그림 base64)는 사용자 동작마다 하지 않는다.

## 1. 부팅 순서 (`src/main.ts`)

1. `installUiContractGlobals` — 벤더 UI가 쓰는 전역들.
2. `installSettingsUx`, `installNativeBridge` — 설정 화면, 백엔드 라우트.
3. `installTtsHost` (`src/tts-ui/host-chat.ts`) — TTS 줄 버튼. 안에서 TTS 창(`host-viewer.ts`)과 창 드래그(`host-drag.ts`)도 설치.
4. `installInlineTags` — 스트리밍 태그(답장 중 그림 태그).
5. `installWaitTaps` (`src/image-ui/wait-taps.ts`) — 분홍 칸 두 번 탭·꾹 누르기.
6. `installNoteExtras`, `installTagFloat` (`src/image-ui/tag-float.ts`) — 🟪 플로팅 태그.
7. `installOmniViewer` (`src/viewer/omni-viewer.ts`) — 옴니 뷰어(열기 전엔 버튼과 훅만).
8. `installQuickSetup`, `restorePendingShotAssets`.
9. 벤더 UI(`vendor/inlay-nexus-ui.js` + `tools/vendor-patches/*`) — 이벤트 셸(포인터 파이프라인), 플로팅 뷰어
   (`float-viewer*.js`), 설정 감시, 메시지 바로가기툴, 스크롤 붙잡기, 스트리밍 런타임.

## 3. 사용자 동작마다 도는 것

### 3-1. 스크롤 (`scroll`/`scrollend`, 문서 캡처)
| 듣는 곳 | 하는 일 |
|---|---|
| 벤더 스크롤 버스 | 스크롤 상태 기록 (호출 없음) |
| 플로팅 뷰어 | 0.15초마다 "화면 가운데 그림" 스캔: 채팅 화면·body 조회, 화면 크기, 가운데 근처 메시지 3개 크기, 새로 가까워진 메시지 감시자 설치, 그림 읽기 → 그림이 바뀌면 src 읽어서 뷰어에 다시 씀 |
| TTS 줄 버튼 (e1555e7) | **0.4초마다 전체 스캔**: 캐릭터 전체 읽기 + 모든 메시지의 모든 줄 버튼(묶기·접힘 확인·크기) |

측정(스크롤 3초): 왕복 244 (TTS 133, 뷰어 109). **멈춘 뒤에도** TTS 스캔이 밀려서 4초간 174왕복.

### 3-2. 누르기 (`pointerdown`)
| 듣는 곳 | 하는 일 |
|---|---|
| 벤더 포인터 셸 | 제스처 시작, 그림 꾹 누르기 판정, 기록 터치 |
| **플로팅 뷰어** | 손잡이 5개 크기 → 끌기 후보면 **버튼 26~31개를 하나씩 조회·측정**(약 50왕복) 뒤에야 드래그 시작 |
| TTS 창 드래그 | 머리줄 조회 + 크기 (+창 크기·문서 크기) — 어디를 누르든 |
| TTS 창 | 창 크기 (어디를 누르든) |
| 분홍 칸 | 0.3초 머물면 칸 찾기 |

### 3-3. 끌기 (`pointermove`)
| 듣는 곳 | 하는 일 |
|---|---|
| 벤더 포인터 셸 | 기록 호버, 이동량, **뷰어 켜져 있으면 "커서 근처 그림"** |
| 플로팅 뷰어 | 드래그 중이면 `transform` 쓰기 (한 번에 최대 16개 대기) |
| TTS 창 드래그 | 드래그 중이면 `transform` 쓰기 |

측정: 조용할 때 뷰어 첫 이동까지 1.06초(이동 지연 중간값 156ms). **스크롤 직후·스트리밍 중엔 드래그가 시작조차 안 됨 (0/40)** — 버튼 50왕복을 기다리는 사이 손을 뗌.

### 3-4. 탭 (`click`)
| 듣는 곳 | 하는 일 |
|---|---|
| 벤더 메시지 선택 | 메시지 목록 + 위치 (메시지 수만큼) |
| **플로팅 뷰어** | 뷰어 위면 **버튼 전부 조회·측정**(약 60왕복) 후 버튼 실행 |
| **TTS 줄 버튼 (e1555e7)** | TTS 창 위인지 확인 + **모든 줄 버튼 위치 측정** + 0.15초 뒤 전체 스캔 |
| TTS 창 | 창 크기 → 위면 버튼 측정 |
| 분홍 칸 | 모든 칸 측정 (두 번 탭 판정용) |
| 🟪 | 들고 있는 위치로 판정 (호출 없음) |

측정: 줄 탭 → 재생 **4.4초**(스캔에 밀림). 그림 두 번 탭 100왕복. 뷰어 접기 버튼 → 접힌 모습 2.5초 안에 안 보임.

### 3-5. 채팅이 바뀔 때 (스트리밍 청크, 그림 채워짐, 새 메시지)
| 듣는 곳 | 하는 일 |
|---|---|
| TTS 줄 버튼 | 0.2초 뒤 전체 스캔 (스캔 중이면 끝나고 한 번 더) |
| 플로팅 뷰어 | 목록 바뀜 → 위치 정보 버림 → 다시 스캔; 가까운 메시지 내용 바뀜 → 그 메시지 다시 읽기 |
| 스크롤 붙잡기 | 스트리밍 중 보던 곳 기록 |
| 바로가기툴 | 미리보기 칸 그리기 |

측정(10청크): 184왕복, 캐릭터 전체 읽기 3.7MB.

### 3-6. 답장 끝 (`onChatOutput`, Risu `output`)
벤더: 바로가기툴·뷰어 스캔 예약. TTS: 자동 읽기면 0.25초 뒤 스캔하고 재생. 옴니 뷰어: 5초 뒤 "얼굴 미리 만들기"(켜져 있으면),
스트리밍 끝 처리. 스트리밍 태그: 박제.

### 3-7. 설정 저장
TTS 설정(창 이동·접기·볼륨·패널 포함) → TTS 줄 버튼 **전체 스캔** + TTS 창 다시 그리기. BGM·효과음 설정 → 전체 스캔.
측정: TTS 창 끌기 뒤 2.5초간 386왕복.

## 4. "Risu 구조상 이게 최선인가" — 판정

| # | 지금 구조 | 판정 | v3에서 가능한 더 나은 방법 |
|---|---|---|---|
| 1 | 플로팅 뷰어: 누르기·탭마다 버튼 26~31개 위치를 Risu에 물음 | **최선 아님** | 뷰어를 그린 뒤 한 번 재서 들고 있기(🟪 플로팅 태그가 이미 이 방식). 누르기·탭은 0왕복 |
