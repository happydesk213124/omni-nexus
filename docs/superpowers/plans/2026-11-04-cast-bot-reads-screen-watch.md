> 상태: 계획 (2026-11-04). 검토를 받은 뒤 1 → 2 → 3 순서로, 단계마다 따로 커밋하고 빌드해 폰에서 확인한다.
> 오전에 만들었다가 되돌린 `adf890b`의 세 가지를 다시 본 것이다. 셋 다 그보다 나은 방법으로 한다.

## 1. 새 인물 등록이 빠지는 문제

### 지금

- 「새 캐릭터를 맨 앞에 쓰기」: 답장 앞쪽의 캐스트 블록이 닫히면, 거기 적힌 새 인물을 등록한다.
- 순서 (`tools/vendor-patches/stream-inline-runtime.js:15-22`, `:39-41`):
  1. 캐스트 블록이 닫힌다.
  2. **'보냈음'(`castSent`) 표시부터 한다.**
  3. 답장 주소(채팅 + 메시지 id)를 찾는다(`omniCaptureKeywordTarget`).
  4. 주소가 없으면 그냥 끝난다. 이미 '보냈음'이라 다시 시도하지 않는다.
- 주소 찾기(`stream-keyword-runtime.js:19-24`)는 Risu 범위 읽기 `Z()`를 쓴다.
  - `Z()`는 봇 전체(그 봇의 모든 채팅)를 읽고, 같은 채팅을 또 한 번 읽는다.
  - 다 읽은 뒤 "아직 스트리밍 중인가"를 본다. 긴 채팅에서는 읽기가 늦게 돌아와 스트리밍이 이미 끝나 있고, 그러면 주소가 없다고 나온다.
  - 답장 처리가 취소되거나 보내다 오류가 나도 마찬가지로 사라진다.
- 결과: 새 인물이 등록되지 않는다. 그림 블록은 새 인물을 캐스트에 맡기도록 되어 있어서, 그 인물은 아무 데도 들어가지 않는다.

### 주소가 필요한 것과 필요 없는 것

'주소'는 채팅 안의 **어느 메시지(어느 답장)인지**다.

| 하는 일 | 필요한 것 |
|---|---|
| 새 인물 등록 ("이 채팅에 새 사람이 나왔다") | 채팅만 |
| 장소 기억 ("이 답장은 교실에서 일어났다": 뒤 그림이 이어받는 장면 위치, 옴니 뷰어 배경) | 채팅 + 메시지(주소) |
| 그림 박제 | 채팅 + 메시지(주소) |

지금은 등록과 장소 기억이 한 요청(`/v1/inline-tags/cast`, `src/services/inline-cast.ts`)에 묶여 있다. 그래서 등록까지 주소를 기다린다.

### 나누지 않는 이유 (구현하며 확인)

- 그림 블록도 답장 주소를 알 때까지 기다린다(`stream-inline-runtime.js`, `if(!final && !run.identity)`).
- 그림은 앞 블록의 등장인물 등록이 끝난 뒤에 시작한다(`stream-continuity.ts`의 `earlierRosterWrites`).
- 그래서 캐스트가 **같은 주소로 그림보다 먼저** 가면, 새 인물은 그 답장의 어느 그림보다도 먼저 등록된다. 등록을 주소보다 먼저 할 이유가 없다.
- 둘로 나누면 받는 쪽 요청을 쪼개고, 등록이 끝나기 전에 그림이 시작하지 않게 막는 장치가 더 필요하다. 복잡함만 는다.
- 오전 수정(`adf890b`)은 주소 없이 보내서, 장소 기억이 저장되지 않았다(`stream-continuity.ts:26-28`, `viewer-places.ts:21`: 메시지 id가 없으면 기록 안 함).

### 바꾸는 방법

1. **버리지 않기**
   - '보냈음'은 실제로 보낸 뒤에만 표시한다.
   - 주소를 아직 모르면 그림 블록과 함께 기다린다. 캐스트 블록이 닫히면 주소를 다시 묻는다.
   - 스트리밍 중에는 한 번만 시도한다(조각마다 다시 보내지 않는다). 그게 실패하거나 끝까지 주소를 몰랐으면, 답장이 끝날 때 한 번 더 보낸다(끝날 때는 주소가 항상 있다).
   - 그림이 없는 답장은 끝날 때 처리가 취소되는데(`stream-lines-runtime.js:47`), 끝난 답장의 캐스트는 취소돼도 보낸다.
2. **주소 묻기를 한곳에서**
   - 답장 시작 때와 그림 블록이 닫힐 때 같은 코드가 두 벌 있었다. 하나(`omniAskInlineTarget`)로 합쳐 캐스트도 같이 쓴다.
3. **주소를 가볍게 찾기 → 2번으로 옮긴다**
   - 주소와 같이 오는 정보에 봇 설명·성격이 들어 있고, 그림 작업이 이걸 쓴다(`stream-keyword-runtime.js`의 `omniStartKeywordJob`).
   - 들고 있던 화면 정보로 바꾸면, 봇 설명을 고쳐도 채팅을 바꿀 때까지 옛 설명이 쓰인다.
   - 2번(같은 작업 안에서 봇 넘겨주기)으로 요청 때 읽은 최신 봇을 넘겨받으면 이 문제가 없다. 그래서 2번에서 같이 한다.

### 효과

- 새 인물이 빠지지 않는다. 주소를 알면 그 답장의 첫 그림보다 먼저, 몰랐으면 답장 끝에 등록된다.
- 장소 기억(뒤 그림의 장면 위치, 옴니 뷰어 배경)도 지금처럼 남는다.

### 테스트

- 주소를 알면 캐스트가 첫 그림보다 먼저, 메시지 id와 함께 한 번 간다. 답장 끝에 다시 가지 않는다.
- 주소 읽기가 스트리밍이 끝난 뒤에 돌아와도 캐스트를 버리지 않고 답장 끝에 보낸다.
- 그림 없는 답장도 끝날 때 캐스트를 보낸다.
- 실패하면 답장 끝에 한 번 더 보내고, 보낸 뒤로는 다시 보내지 않는다. 조각마다 다시 시도하지 않는다.
- 위의 버그 테스트 셋은 옛 코드에서 실패한다(확인함).

## 2. 봇 정보를 너무 많이 읽는 문제

### 지금

- 등장인물 목록(봇 로어북 안에 저장)이 필요하면 (`src/storage/character-roster.ts:24-46`):
  1. **모든 봇이 든 목록**을 받는다(`characterDirectory` → `getDatabase(['characters'])`). 원본 Risu에서는 모든 봇의 모든 채팅까지 같이 온다. 2초 동안은 다시 쓴다.
  2. 그 목록에서 봇을 찾는다.
  3. 그 봇을 **또** 받는다(`getCharacterFromIndex`).
- 에셋 태그(`src/services/character-source.ts:13-30`)도 같은 목록으로 봇을 찾고 다시 받는다.
- 답장 중 그림 태그 요청 한 번에:
  - 요청 시작 때 봇 전체 1번(`src/services/inline-tagging.ts:144-146`)
  - 등장인물 목록용으로 모든 봇 목록 1번 + 봇 1번
  - 에셋 태그용으로 봇 1번
- 모든 봇 목록을 직접 받는 곳: 8개 파일.
  - 등장인물 목록(`character-roster.ts`), 봇 읽기(`character-source.ts`)
  - 박제(`chat-bake.ts`), 세션(`chat-session-store.ts`), 샷 캐릭터(`shot-character.ts`), TTS 로스터(`tts-roster.ts`)
  - 에셋 메시지(`asset-message.ts`), 설정 연결(`settings-ux/risu-bindings.ts`)
- 등장인물 목록과 봇 읽기를 거쳐 쓰는 곳은 13군데다(에셋 태그, 캐스트 id, 이미지 준비, 캐릭터 가져오기 등).
- 오전에 무거운 가짜 Risu(봇 10개 × 채팅 5개, 한 채팅에 메시지 500개)로 잰 값: 요청 한 번에 4.47MB(호출 11번).

### 오전 수정과의 차이

- 오전: 요청 시작 때 읽은 봇을 5초 동안 기억해서, 같은 요청 안에서만 다시 썼다.
- 이번: **지금 열린 봇이면 처음부터 모든 봇 목록을 받지 않는다.** 그림 태그 요청뿐 아니라, 등장인물 목록과 봇 읽기를 거치는 13군데 모두에 해당한다.
- 나머지 6개 파일(박제, 세션, 샷 캐릭터, TTS 로스터, 에셋 메시지, 설정 연결)은 이번에 바꾸지 않는다. 쓰기가 섞여 있거나 다른 봇이 필요할 수 있어서, 하나씩 확인한 뒤 따로 한다.

### 바꾸는 방법

1. **'지금 봇 읽기' 하나** (새 파일 `src/storage/current-bot.ts`)
   - 지금 봇 번호를 묻고(작은 호출), 그 봇 하나만 읽는다.
   - 여러 곳에서 **같은 순간에** 물으면 한 번만 읽고 나눠 쓴다. 읽기가 끝나면 바로 잊는다.
   - **시간으로 기억하지 않는다.** 그래서 Risu에서 봇을 고친 직후에 옛 정보를 쓰는 틈이 없다.
2. **같은 작업 안에서는 넘겨주기**
   - 그림 태그 요청은 시작할 때 봇을 한 번 읽는다(`inline-tagging.ts`의 `liveScope`).
   - 그 봇을 다음 단계(등장인물 목록, 에셋 태그)에 직접 건넨다. 다음 단계는 그걸 받으면 다시 읽지 않는다.
   - 건넬 수 있게 `readCharacterRoster`, `characterSource`, `collectAssetNaiTags`가 봇을 선택 인자로 받는다.
3. **읽을 때는 지금 봇부터**
   - 등장인물 목록, 에셋 태그가 대상이다(건네받은 봇이 없을 때).
   - 찾는 봇이 지금 봇(id·통합 범위·그 봇 채팅들의 세션 id로 확인)이면 그 봇을 그대로 쓴다. 모든 봇 목록은 받지 않는다.
   - 다른 봇일 때만 지금처럼 모든 봇 목록으로 찾는다.
4. **저장할 때는 지금 그대로**
   - 모든 봇 목록을 새로 받아서 확인한다. 같은 id를 가진 봇이 둘이면 막는 장치라 그대로 둔다.
5. **답장 주소를 가볍게 찾기** (1번에서 옮겨 옴)
   - 답장 주소 찾기(`omniCaptureKeywordTarget`)는 지금 `Z()`로 봇 전체(모든 채팅)를 읽고 같은 채팅을 또 읽는다. 긴 채팅에서는 이게 늦어서 스트리밍이 끝난 뒤에 돌아온다.
   - 그림 태그 요청이 시작할 때 읽은 봇(이 답장의 요청을 만든 바로 그 봇)을 넘겨받는다. 봇 id·채팅 id·설명·성격은 거기서 쓴다.
   - 그래서 주소 찾기는 **지금 채팅 하나만** 읽는다(`getChatFromIndex`). 마지막 메시지가 스트리밍 중인 답장이고, 그 id가 주소다. 화면 번호가 맞는지는 작은 호출 2개로 확인한다.
   - 넘겨받은 봇이 없거나(그림 태그 요청이 아닌 답장) 화면 번호가 다르면 지금처럼 `Z()`로 읽는다.
   - 그림 블록도 같은 주소 찾기를 쓰므로, **답장 중 그림도 더 빨리 시작**한다.

### 효과

- 그림 태그 요청 한 번: 모든 봇 목록 1번 → 0번, 봇 읽기 3번 → 1번.
- 등장인물 목록과 봇 읽기를 거치는 다른 곳도, 지금 봇이면 모든 봇 목록을 받지 않는다.
- 한계: Risu v3에는 "채팅 빼고 봇 정보만" 주는 기능이 없다. 그래서 봇 하나는 그 봇의 채팅들과 함께 온다. 요청 한 번에 1번이 최선이다.

### 테스트

- 지금 봇의 등장인물을 읽을 때 모든 봇 목록을 받지 않는다.
- 다른 봇의 등장인물은 여전히 모든 봇 목록으로 찾는다.
- 같은 순간에 여러 곳에서 물어도 봇을 한 번만 읽는다.
- 읽기가 끝난 뒤에 다시 물으면 새로 읽는다(시간 메모 없음).
- 그림 태그 요청 안의 등장인물·에셋 태그는 건네받은 봇을 쓰고 다시 읽지 않는다.
- 답장 주소 찾기는 넘겨받은 봇이 있으면 채팅 하나만 읽고, 그림 작업의 봇 설명은 요청 때 읽은 것이다.
- 저장은 모든 봇 목록 확인을 거친다.
- 그림 태그 요청 한 번에 봇 읽기 1번, 모든 봇 목록 0번. 오전과 같은 무거운 가짜 Risu로 크기를 잰다.

## 3. 화면 확인 합치기

### 지금 — 각자 따로 묻는다

| 누가 | 얼마나 자주 | 무엇을 | 언제 |
|---|---|---|---|
| TTS 창 (`src/tts-ui/host-viewer.ts:242-259`) | 1초마다 | 채팅 화면 찾기 + 크기 (호출 2개 + 해제) | **TTS를 꺼도** (창은 TTS를 켰을 때만 보인다: `:52`, `:59`) |
| 플로팅 태그 (`src/image-ui/tag-float.ts:218-239`) | 2초마다 | 채팅 화면 찾기 + 크기 (호출 2개 + 해제) | 플로팅 태그를 켰을 때 |
| Risu 설정창 감시 (`vite.config.ts`의 `startRisuSettingsViewerWatch`, `host-traffic.mjs` 5번) | 평소 3.2초마다, 탭한 직후 1.6초 동안은 0.4초마다 | 설정창이 열렸나 (호출 1개) | 항상 |

- TTS 창과 플로팅 태그는 같은 걸(채팅 화면이 보이나, 크기가 얼마인가) 따로 묻는다. 둘 다 켜면 1초에 3번이다.
- Risu 설정창 감시는 설정창이 열리면 플로팅 뷰어를 숨기고, 닫히면 다시 띄운다.

### Risu 설정창은 어떻게 그려지나 (Risu 원본에서 확인)

- 설정창은 채팅 위에 덮이는 창이 아니다. **채팅 화면을 빼고 그 자리에 그려지는 일반 페이지다**(Risu `App.svelte`의 `{:else if $settingsOpen} <Settings />`, 채팅 화면 `ChatScreen`과 둘 중 하나만 그려짐).
- 그래서 z값으로는 못 가린다. 우리 뷰어는 화면 고정(`position:fixed`)이라 z값이 0 이상이면 일반 페이지 위에 늘 뜬다. 음수로 하면 평소 채팅 아래로도 숨는다.
- 대신 **설정창이 열리면 채팅 화면이 사라진다.** 그러니 "채팅 화면이 없으면 숨긴다" 하나면 된다. 설정창을 따로 검사할 필요가 없다.

### 바꾸는 방법

1. **채팅 화면 지킴이 하나** (새 파일 `src/services/chat-screen-watch.ts`)
   - 채팅 화면(`.default-chat-screen`)을 들고 있다가 1초에 한 번 크기만 잰다(호출 1개).
   - 크기가 0이면(화면이 바뀌었거나 사라짐) 그때만 다시 찾는다.
   - 탭하면 0.3초 뒤에 한 번 더 본다. 설정창은 탭으로 열리니, 지금 설정창 감시의 "탭 직후 빨리 보기"와 같은 속도로 숨는다.
   - 알려 주는 것: 채팅이 화면에 있는지, 크기가 얼마인지. 바뀌었을 때만 알린다.
   - 지켜볼 곳이 없으면(TTS, 플로팅 태그, 플로팅 뷰어가 모두 꺼짐) 쉰다. 아무것도 묻지 않는다.
2. **TTS 창, 플로팅 태그, 플로팅 뷰어는 직접 묻지 않는다**
   - 지킴이의 결과를 받아 쓴다. TTS가 꺼져 있으면 TTS 창은 지킴이에 등록하지 않는다(오전 수정의 "꺼지면 안 묻기"가 여기 들어간다).
   - 플로팅 태그가 크기 변화로 다시 재던 것(`screenSig`)도 지킴이의 크기로 한다.
   - 플로팅 뷰어는 채팅이 사라지면 숨고, 돌아오면 다시 뜬다. 벤더 안쪽 코드라, 지킴이가 연결 하나(`__OMNI_CHAT_SCREEN__`)로 알린다(이미 쓰는 `__OMNI_CHAT_COVER__`와 같은 방식).
3. **Risu 설정창 감시를 없앤다**
   - 주기 감시(평소 3.2초, 탭 직후 0.4초마다)와 그 숨김·복원 처리를 지운다.
   - 설정창뿐 아니라 캐릭터 목록처럼 채팅이 없는 다른 화면에서도 똑같이 숨는다.
   - Risu '빠른 설정'은 다른 이름표(`rs-setting-cont-5`)라 지금 감시에도 안 걸린다. 바뀌는 건 없다.
   - 우리 설정을 닫을 때 Risu 설정으로 돌아갈지 정하려고 한 번 묻는 곳(`isRisuSettingsOpen`)은 그대로 둔다. 주기적으로 묻는 게 아니다.

### 효과

| 켜 둔 것 | 지금 (1초에) | 바꾸면 |
|---|---|---|
| TTS + 플로팅 태그 + 플로팅 뷰어 | 약 3.3번 (탭 직후엔 더) | 1번 (탭하면 1번 더) |
| TTS만 | 2.3번 | 1번 |
| 플로팅 태그만 | 3.3번 (TTS 창이 꺼진 채로 2번 헛묻기) | 1번 |
| 모두 끔 | 2.3번 (TTS 창 헛묻기 + 설정창 감시) | 0번 |

(설정창 감시는 평소 3.2초에 한 번이라 1초에 약 0.3번으로 셌다.)

### 테스트

- TTS, 플로팅 태그, 플로팅 뷰어를 모두 켜도 1초에 크기 읽기 1번이다.
- 채팅 화면이 바뀌면 모두 알게 되고, 다시 찾기는 1번이다.
- 모두 끄면 0호출이다.
- TTS만 끄면 TTS 창은 아무것도 묻지 않는다.
- 채팅 화면이 사라지면(설정창이 열림) 플로팅 뷰어가 숨고, 돌아오면 다시 뜬다. 탭한 뒤에는 1초를 기다리지 않고 숨는다.
- 설정창을 주기적으로 묻는 호출이 없다.
- 위 테스트는 각각 일부러 깨뜨려서 실패하는지 확인한다(타이밍 테스트).

## 진행

- 1 → 2 → 3 순서로, 단계마다 따로 커밋한다.
- 단계마다 실험실에서 호출 수와 읽는 데이터 크기를 재고, 빌드를 보내 폰에서 확인한다.
- 세 단계가 끝나면 전체 테스트를 한 번 돌린다.

## 확인 필요

- 없음. 2번의 시간 메모는 빼고(같은 순간 나눠 쓰기 + 작업 안 넘겨주기), 3번은 설정창 감시를 없애고 "채팅 화면이 없으면 숨김"으로 한다.
