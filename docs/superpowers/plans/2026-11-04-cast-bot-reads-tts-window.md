> 상태: 계획 (2026-11-04). 검토를 받은 뒤 1 → 2 → 3 순서로, 단계마다 따로 커밋하고 빌드해 폰에서 확인한다.
> 오전에 만들었다가 되돌린 `adf890b`의 세 가지를 다시 본 것이다. 1·2는 그보다 나은 방법으로, 3은 그대로 한다.

## 1. 새 인물 등록이 빠지는 문제

### 지금

- 「새 캐릭터를 맨 앞에 쓰기」: 답장 앞쪽의 캐스트 블록이 닫히면, 거기 적힌 새 인물을 등록한다.
- 순서 (`tools/vendor-patches/stream-inline-runtime.js:15-22`, `:39-41`):
  1. 캐스트 블록이 닫힌다.
  2. **'보냈음'(`castSent`) 표시부터 한다.**
  3. 답장 주소(채팅 + 메시지 id)를 찾는다(`omniCaptureKeywordTarget`).
  4. 주소가 없으면 그냥 끝난다. 이미 '보냈음'이라 다시 시도하지 않는다.
- 주소 찾기(`stream-keyword-runtime.js:19-24`)는 Risu 범위 읽기 `Z()`를 쓴다.
  - `Z()`는 봇 전체(그 봇의 모든 채팅)를 읽고, 같은 채팅을 또 한 번 읽는다.
  - 다 읽은 뒤 "아직 스트리밍 중인가"를 본다. 긴 채팅에서는 읽기가 늦게 돌아와 스트리밍이 이미 끝나 있고, 그러면 주소가 없다고 나온다.
  - 답장 처리가 취소되거나 보내다 오류가 나도 마찬가지로 사라진다.
- 결과: 새 인물이 등록되지 않는다. 그림 블록은 새 인물을 캐스트에 맡기도록 되어 있어서, 그 인물은 아무 데도 들어가지 않는다.

### 오전 수정(`adf890b`)을 그대로 쓰지 않는 이유

- 오전 수정은 주소 없이 채팅만으로 바로 보냈다. 등록은 되지만, 메시지 id가 비면 두 가지가 저장되지 않는다.
  - 뒤따르는 그림 블록이 이어받는 장면 위치(`src/services/stream-continuity.ts:26-28`: 메시지 id가 없으면 기록 안 함)
  - 옴니 뷰어가 기억하는 이 답장의 장소(`src/storage/viewer-places.ts:21`: 메시지 id가 없으면 저장 안 함)
- 그림 블록도 답장 주소를 알 때까지 기다린다(`stream-inline-runtime.js:51-62`). 그래서 캐스트를 주소보다 먼저 보낼 이유가 없다. 같은 주소로 그림보다 먼저 보내면 된다.

### 바꾸는 방법

1. **버리지 않기**
   - '보냈음'은 실제로 보낸 뒤에만 표시한다.
   - 주소를 아직 못 찾았으면 기다린다. 주소를 찾으면 바로 보내고, 끝까지 못 찾으면 답장이 끝날 때 보낸다(끝날 때는 주소가 항상 있다).
   - 보내다 오류가 나면 답장이 끝날 때 한 번 더 보낸다. 두 번 보내지는 않는다.
   - 그림이 없는 답장(캐스트만 있는 답장)도 보낸다.
2. **주소를 가볍게 찾기**
   - 봇 전체 대신 **지금 채팅 하나만** 읽는다(`getChatFromIndex`). 마지막 메시지가 스트리밍 중인 답장이고, 그 id가 주소다.
   - 봇 id와 채팅 id는 이미 들고 있는 화면 정보(`omniScope`)를 쓴다. 지금 화면 번호와 맞는지는 작은 호출 2개로 확인한다.
   - 들고 있는 정보가 없거나 화면 번호가 다르면 지금처럼 `Z()`로 읽는다.
   - 그림 블록도 같은 주소 찾기를 쓰므로, **답장 중 그림도 더 빨리 시작**한다.
3. **순서**: 캐스트는 그림 블록과 같은 주소로, 그림보다 먼저 간다. 장면 위치와 뷰어 장소도 지금처럼 저장된다.

### 효과

- 새 인물이 빠지지 않는다.
- 주소 찾기 한 번에 읽는 양: 봇 전체 + 채팅 → 채팅 하나.

### 테스트

- 주소 읽기가 스트리밍이 끝난 뒤에 돌아와도, 캐스트가 답장 끝에 보내진다. (옛 동작을 되돌리면 실패해야 한다.)
- 보내다 오류가 나면 답장 끝에 한 번 더 보내고, 성공하면 다시 보내지 않는다.
- 그림 없는 답장도 캐스트를 보낸다.
- 보낸 캐스트에는 메시지 id가 있어서 장면 위치가 기록된다.
- 주소 찾기가 봇 전체를 읽지 않는다(들고 있는 정보가 있을 때).

## 2. 봇 정보를 너무 많이 읽는 문제

### 지금

- 등장인물 목록(봇 로어북 안에 저장)이 필요하면 (`src/storage/character-roster.ts:24-46`):
  1. **모든 봇이 든 목록**을 받는다(`characterDirectory` → `getDatabase(['characters'])`). 원본 Risu에서는 모든 봇의 모든 채팅까지 같이 온다. 2초 동안은 다시 쓴다.
  2. 그 목록에서 봇을 찾는다.
  3. 그 봇을 **또** 받는다(`getCharacterFromIndex`).
- 에셋 태그(`src/services/character-source.ts:13-30`)도 같은 목록으로 봇을 찾고 다시 받는다.
- 답장 중 그림 태그 요청 한 번에:
  - 요청 시작 때 봇 전체 1번(`src/services/inline-tagging.ts:144-146`)
  - 등장인물 목록용으로 모든 봇 목록 1번 + 봇 1번
  - 에셋 태그용으로 봇 1번
- 모든 봇 목록을 직접 받는 곳: 8개 파일.
  - 등장인물 목록(`character-roster.ts`), 봇 읽기(`character-source.ts`)
  - 박제(`chat-bake.ts`), 세션(`chat-session-store.ts`), 샷 캐릭터(`shot-character.ts`), TTS 로스터(`tts-roster.ts`)
  - 에셋 메시지(`asset-message.ts`), 설정 연결(`settings-ux/risu-bindings.ts`)
- 등장인물 목록과 봇 읽기를 거쳐 쓰는 곳은 13군데다(에셋 태그, 캐스트 id, 이미지 준비, 캐릭터 가져오기 등).
- 오전에 무거운 가짜 Risu(봇 10개 × 채팅 5개, 한 채팅에 메시지 500개)로 잰 값: 요청 한 번에 4.47MB(호출 11번).

### 오전 수정과의 차이

- 오전: 요청 시작 때 읽은 봇을 5초 동안 기억해서, 같은 요청 안에서만 다시 썼다.
- 이번: **지금 열린 봇이면 처음부터 모든 봇 목록을 받지 않는다.** 그림 태그 요청뿐 아니라, 등장인물 목록과 봇 읽기를 거치는 13군데 모두에 해당한다.
- 나머지 6개 파일(박제, 세션, 샷 캐릭터, TTS 로스터, 에셋 메시지, 설정 연결)은 이번에 바꾸지 않는다. 쓰기가 섞여 있거나 다른 봇이 필요할 수 있어서, 하나씩 확인한 뒤 따로 한다.

### 바꾸는 방법

1. **'지금 봇 읽기' 하나** (새 파일 `src/storage/current-bot.ts`)
   - 지금 봇 번호를 묻고(작은 호출), 그 봇 하나만 읽는다.
   - 여러 곳에서 동시에 물으면 한 번만 읽고 나눠 쓴다.
   - 2초 동안은 다시 쓴다. 모든 봇 목록이 이미 쓰는 방식과 같다.
   - 우리가 봇을 저장하면(등장인물, 로어북, 샷 에셋, TTS 로어북) 바로 버린다. 저장 뒤 옛 정보를 읽는 일은 없다.
2. **읽을 때는 지금 봇부터**
   - 등장인물 목록, 에셋 태그, 그림 태그 요청 시작이 대상이다.
   - 찾는 봇이 지금 봇(id·통합 범위·그 봇 채팅들의 세션 id로 확인)이면 그 봇을 그대로 쓴다. 모든 봇 목록은 받지 않는다.
   - 다른 봇일 때만 지금처럼 모든 봇 목록으로 찾는다.
3. **저장할 때는 지금 그대로**
   - 모든 봇 목록을 새로 받아서 확인한다. 같은 id를 가진 봇이 둘이면 막는 장치라 그대로 둔다.

### 효과

- 그림 태그 요청 한 번: 모든 봇 목록 1번 → 0번, 봇 읽기 3번 → 1번.
- 등장인물 목록과 봇 읽기를 거치는 다른 곳도, 지금 봇이면 모든 봇 목록을 받지 않는다.
- 한계: Risu v3에는 "채팅 빼고 봇 정보만" 주는 기능이 없다. 그래서 봇 하나는 그 봇의 채팅들과 함께 온다. 요청 한 번에 1번이 최선이다.

### 테스트

- 지금 봇의 등장인물을 읽을 때 모든 봇 목록을 받지 않는다.
- 다른 봇의 등장인물은 여전히 모든 봇 목록으로 찾는다.
- 같은 순간에 여러 곳에서 물어도 봇을 한 번만 읽는다.
- 우리가 저장한 뒤에는 새로 읽는다(저장 전 정보를 쓰지 않는다).
- 저장은 모든 봇 목록 확인을 거친다.
- 그림 태그 요청 한 번에 봇 읽기 1번, 모든 봇 목록 0번. 오전과 같은 무거운 가짜 Risu로 크기를 잰다.

## 3. TTS 창의 1초 확인

### 지금

- 0.5초 틱의 두 번에 한 번(1초마다), 채팅 화면을 찾고 크기를 잰다(호출 2개 + 해제). 창을 보일지 정하려고 하는 일이다(`src/tts-ui/host-viewer.ts:242-259`).
- 창과 알림은 TTS를 켰을 때만 보인다(`host-viewer.ts:52`, `:59`). 그런데 확인은 TTS를 꺼도 계속한다.

### 바꾸는 방법 (오전 수정 그대로)

- TTS가 꺼져 있으면 아무것도 묻지 않는다.
- TTS가 켜져 있으면 채팅 화면을 들고 있다가 크기만 잰다(호출 1개). 크기가 0이면(화면이 바뀌었거나 사라짐) 그때만 다시 찾는다.

### 효과

- TTS 꺼짐: 1초에 2번 → 0번.
- TTS 켜짐: 1초에 2번 → 1번.

### 나중에 (입력 허브 단계)

- TTS 창(1초), 플로팅 태그(2초), 설정창 감시(0.4초)가 각자 따로 화면을 확인한다. 이걸 하나로 합친다. 이번 계획에는 넣지 않는다.

### 테스트

- TTS 꺼짐: 0호출.
- TTS 켜짐: 1초에 크기 읽기 1번, 화면 찾기 0번.
- 채팅 화면이 바뀌면 다시 찾는다.
- 위 셋은 각각 일부러 깨뜨려서 실패하는지 확인한다(타이밍 테스트).

## 진행

- 1 → 2 → 3 순서로, 단계마다 따로 커밋한다.
- 단계마다 실험실에서 호출 수와 읽는 데이터 크기를 재고, 빌드를 보내 폰에서 확인한다.
- 세 단계가 끝나면 전체 테스트를 한 번 돌린다.

## 확인 필요

1. 1번에서 답장이 끝날 때까지 주소를 못 찾으면, 새 인물 등록도 답장 끝으로 미뤄진다. 그림 블록도 같은 주소를 기다리므로 그림에는 문제가 없다. 다만 답장 도중에 등장인물 목록을 읽는 곳(TTS의 인물·의상 이름 같은 것)은 새 인물을 늦게 알게 될 수 있다. 이대로 괜찮은지.
2. 2번의 '2초 다시 쓰기': Risu 화면에서 봇을 직접 고친 뒤 2초 안에 그림 태그 요청이 가면, 고치기 전 정보를 쓸 수 있다. 모든 봇 목록이 지금도 2초 동안 같은 방식이라 같은 수준이다. 괜찮은지.
